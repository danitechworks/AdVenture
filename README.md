# AdVenture

**A RESTful ASP.NET Core Web API for managing classified advertisements.**

AdVenture is a controller-based Web API developed using C#, ASP.NET Core, Entity Framework Core, and SQL Server. It provides CRUD functionality for classified advertisements, including full and partial updates, data validation, and appropriate HTTP responses.

The project was developed as an individual assignment for the *Programmering med C# .NET* course at YH Akademin.

## Technologies

- **C# / .NET 10**
- **ASP.NET Core Web API** — Controller-based architecture
- **Entity Framework Core 10** — Code First database management
- **SQL Server** — Relational database
- **LINQ** — Database queries
- **Swagger UI / OpenAPI** — Interactive API documentation and testing

## Features

- Retrieve all advertisements
- Retrieve an individual advertisement by ID
- Create new advertisements
- Update an entire advertisement using HTTP PUT
- Partially update an advertisement using HTTP PATCH
- Delete advertisements
- Validate incoming data using Data Annotations
- Return appropriate HTTP status codes
- Automatically initialize the database with sample data

## Getting Started

### Prerequisites

Before running the application, ensure you have:

- .NET 10 SDK
- Visual Studio with ASP.NET and web development support, or another compatible IDE
- SQL Server (LocalDB, Express, or a compatible SQL Server instance)

### 1. Clone the Repository

```bash
git clone https://github.com/danitechworks/AdVenture.git
cd AdVenture
```

Open `AdVenture.slnx` in Visual Studio.

### 2. Configure the Database Connection

Open `AdVenture/appsettings.json` and locate:

`ConnectionStrings:DefaultConnection`

The default configuration connects to SQL Server on `localhost`, using Windows authentication and a database named `AdVenture`.

If your SQL Server configuration differs, update the connection string accordingly. The configured account needs permission to create or migrate the database.

### 3. Run the Application

In Visual Studio, select the **https** launch profile and press **F5**.

Alternatively, from the repository root:

```bash
dotnet run --project AdVenture --launch-profile https
```

### 4. Automatic Database Initialization

AdVenture automatically initializes its SQL Server database when the application starts.

The initialization process:

1. Applies pending EF Core migrations, creating the database and schema on first run.
2. Checks whether the `Ads` table contains any records.
3. Inserts 15 sample advertisements if the table is empty.
4. Preserves existing advertisements if data is already present.

**No manual database creation or migration commands are required.**

### 5. Open Swagger UI

Swagger UI is available at:

`https://localhost:7000/`

*The port may vary depending on the application's launch settings.*

Swagger provides an interactive interface where all API endpoints can be tested directly.

To verify that the application is running correctly, execute `GET /Ads`. On a fresh database, the response should contain the sample advertisements.

## API Endpoints

| HTTP Method | Endpoint | Description |
|---|---|---|
| GET | `/Ads` | Retrieve all advertisements |
| GET | `/Ads/{id}` | Retrieve an advertisement by ID |
| POST | `/Ads` | Create a new advertisement |
| PUT | `/Ads/{id}` | Replace an existing advertisement |
| PATCH | `/Ads/{id}` | Partially update an advertisement |
| DELETE | `/Ads/{id}` | Delete an advertisement |

## Advertisement Model

Each advertisement contains the following properties:

| Property | Data Type | Description |
|---|---|---|
| `id` | integer | Unique identifier, generated by the database |
| `title` | string | Advertisement title |
| `description` | string | Description of the advertised item |
| `price` | decimal | Price in Swedish kronor (SEK) |
| `category` | string | Advertisement category |

Prices are stored as decimal values and represented in JSON using a period as the decimal separator.

## API Request Examples

Try these examples in Swagger UI. For PUT, PATCH, and DELETE, use the ID returned by POST so the examples all operate on the same test advertisement.

### GET — Retrieve All Advertisements

**Endpoint:** `GET /Ads`

Retrieves all advertisements from the database.

**Expected response:** `200 OK`

```json
[
  {
    "id": 1,
    "title": "IKEA MALM Desk",
    "description": "White desk in excellent condition.",
    "price": 650,
    "category": "Furniture"
  }
]
```

### GET — Retrieve an Advertisement by ID

**Endpoint:** `GET /Ads/1`

Retrieves a specific advertisement using its ID.

**Expected responses:**

- `200 OK` — Advertisement found
- `404 Not Found` — Advertisement does not exist

### POST — Create an Advertisement

**Endpoint:** `POST /Ads`

Creates a new advertisement.

**Example request body:**

```json
{
  "title": "Vintage Desk Lamp",
  "description": "Adjustable brass desk lamp in excellent condition.",
  "price": 450,
  "category": "Home Decor"
}
```

**Expected response:** `201 Created`

The database automatically generates the advertisement's ID.

### PUT — Update an Entire Advertisement

**Endpoint:** `PUT /Ads/{id}`

Replaces the editable properties of an existing advertisement.

**Example request body:**

```json
{
  "title": "Vintage Desk Lamp - Updated",
  "description": "Adjustable brass lamp, fully functional.",
  "price": 400,
  "category": "Home Decor"
}
```

Unlike PATCH, PUT requires the complete set of editable properties.

### PATCH — Partially Update an Advertisement

**Endpoint:** `PATCH /Ads/{id}`

Updates only the properties included in the request.

**Example request body:**

```json
{
  "price": 350
}
```

In this example, only the advertisement's price is changed. The title, description, and category retain their existing values.

PATCH can also update multiple properties in a single request:

```json
{
  "title": "Vintage Brass Desk Lamp",
  "price": 375
}
```

### DELETE — Remove an Advertisement

**Endpoint:** `DELETE /Ads/{id}`

Deletes the advertisement with the specified ID.

**Expected responses:**

- `200 OK` — Advertisement deleted
- `404 Not Found` — Advertisement does not exist

## Validation and Error Handling

AdVenture validates incoming request data using **Data Annotations**.

Validation rules include required fields, string-length restrictions, and acceptable price values.

When validation fails, the API rejects the request and returns an appropriate HTTP error response.

### HTTP Status Codes

| Status Code | Description |
|---|---|
| `200 OK` | Request completed successfully |
| `201 Created` | Advertisement successfully created |
| `400 Bad Request` | Invalid request data |
| `404 Not Found` | Requested advertisement does not exist |

The API uses `[ProducesResponseType]` attributes to document possible responses for each controller action. This information is displayed in Swagger UI.

## Testing the API

### Example Validation Tests

| Test Case | Expected Result |
|---|---|
| Missing required title | `400 Bad Request` |
| Title exceeds maximum length | `400 Bad Request` |
| Negative price | `400 Bad Request` |
| Invalid category length | `400 Bad Request` |
| Request for nonexistent advertisement | `404 Not Found` |

The exact validation limits are defined by the Data Annotations in the application models.
